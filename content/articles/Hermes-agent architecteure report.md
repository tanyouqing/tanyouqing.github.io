# Hermes Agent 整体架构介绍

## 1.1 Agent 实现

Hermes agent整体可分为四层：面向用户的**入口层**、负责整个Agent Loop的**核心编排层**、决定agent会什么的**能力层**和**存储及后断层。**

### 1.1.2 Agent Loop：

```plain
用户输入 / 平台消息进入
 → 生成任务 ID 
 → 把用户消息追加到会话历史 
 → 构建或复用缓存的 system prompt 
 → 检查是否需要预压缩上下文 
 → 从对话历史构建 API messages；runtime_provider.py 决定当前走哪个 provider / 哪种 API mode
 → 注入临时 prompt 层；应用 prompt caching 标记 
 → 发起可中断 API 调用
 → 解析响应：若有 tool call 就执行工具并回到消息构建阶段；若是文本响应，就持久化 session、按需 flush memory，然后返回结果。
 → 工具结果回写到对话历史
 → 必要时继续下一轮推理
 → 最终把文本流式返回给 CLI / 网关 / ACP / API Server
```

### 1.1.3 Prompt组装

+ **系统提示词组装：** 在开始模型推理前，`prompt_builder.py` 会将多个不同维度的事实和设定拼装为全局的 System Prompt。这些内容包括：
  - **身份设定与个性：** 从本地的 `SOUL.md` 文件中提取该智能体的基础性格和设定。
  - **长时声明性记忆：** 提取存储环境事实的 `MEMORY.md` 以及记录用户偏好习惯的 `USER.md`。
  - **项目/工作区上下文 ：** 挂载项目特定的上下文文件，如 `AGENTS.md` 和 `.hermes.md`。
  - **工具指令与模型规范：** 向模型注入特定于其底层的指令格式（例如对于 Hermes-3 模型，会在 `<tools>` 的 XML 标签中注入函数调用的规范和 Schema）。
  - **技能目录：** 注入智能体可用的程序化技能。默认情况下，Prompt 中仅加载所有技能的“名称和简短描述”（Level 0），只有在明确需要执行该任务时，才会把对应的 `SKILL.md` 正文加载进上下文。
+ **长期记忆与临时注入 ：** 情景记忆（历史会话）的注入是在AIAgent的system prompt合成阶段补进去：
  - 动态的用户关系记忆不会被塞进 System Prompt 中，系统提示词仅保留纯净的智能体身份与核心指令。
  - 每个回合里先把用户消息追加到当前会话历史，然后建立/复用system prompt缓存，之后再从对话历史构建API messages。 `AIAgent._build_system_prompt()` 会把将 system prompt 与 memory 和 ephemeral prompts 组合。也就是说，长期记忆的注入点，在 Prompt Builder 产出基础 system prompt 之后、正式把消息发给模型之前。
+ **上下文的优化与管理：** 在组装 Prompt 的同时，系统还有两个辅助模块进行容量与成本控制：
  - **提示词缓存：** 通过 `prompt_caching.py` 模块，系统会针对组装好的 Prompt（特别是针对 Anthropic 的模型）自动应用缓存断点（Cache Breakpoints）。这能确保多轮对话中静态的系统提示词部分被缓存，大幅降低 API 成本。
  - **上下文压缩：** 如果随着对话的推进，Prompt 的长度逼近了设定的 Token 阈值，`context_compressor.py` 模块便会介入，对对话历史中的“中间回合”进行有损的语义摘要压缩，防止上下文溢出。

### 1.1.4 工具调用

1. **工具发现与 Prompt 注入**：在发起大模型调用前，系统需要让模型知道当前有哪些工具可用

- **集中式注册表**：Hermes 拥有一个中央工具注册表（`tools/registry.py`），所有工具文件在导入时会自动完成自我注册（Self-register）。
- **动态注入**：系统会根据当前的上下文、匹配到的技能（Skills）以及权限配置，收集可用工具的 Schema（规范说明），并使用专门的 XML 标签 `<tools>` 将这些定义注入到全局的系统提示词（System Prompt）中。

2. **模型推理与工具调用触发**：

- Hermes **默认依赖的底层模型**经过了专门的工具调用和结构化输出训练。当模型在推理后判断需要执行外部动作时，它会按照严格的 XML 格式输出工具调用请求：`<tool_call> {"name": "func", "arguments": {...}} </tool_call>`。
- 针对主流**云端API模型**：系统会自动将本地的工具列表转换成各大厂商官方 API 要求的格式（通常是通过 API 请求中的 `tools=` 参数传给模型）。模型服务端会进行原生的工具解析，并将结构化的工具调用对象直接返回给 Hermes Agent。
- 如果是纯文本输出的**本地开源模型**（mistral、qwen、llama2_json等），Hermes Agent 提供了一套可插拔工具调用解析器，能够正确拦截、提取出模型输出中的函数名和参数，并无缝触发本地的沙箱执行。

3. 拦截、解析与并发调度：Agent Loop 在收到模型输出时，会持续监听是否包含 `<tool_call>` 标签或者数据

- **拦截与分发**：一旦检测到该标签，循环会暂停模型的自然语言生成，并通过 `model_tools.py` 模块中的 `handle_function_call()` 方法对 JSON 参数进行解析和拦截。
- **并发执行**：为了极大降低多工具调用的延迟，如果模型在同一轮次中发起了多个独立的工具调用，系统会通过线程池（`ThreadPoolExecutor`，池大小为 128）并行执行这些工具。这种设计不仅提升了速度，还能防止诸如 Docker 或 Modal 等异步后端环境发生死锁。

4. **结果封装与“预算压力”管理**：工具在沙箱或本地终端执行完毕后，系统需要将结果反馈给模型

- **规范化返回**：系统会将工具的执行结果（如终端的 stdout、文件内容等）打包成对应的响应格式（包括默认 Hermes-3 的 `<tool_response>` 和主流厂商 API 要求的原生结构），并将其追加到当前的对话历史中。
- **预算压力注入**：为了防止模型在遇到错误时陷入无限的工具调用死循环，Hermes 实现了一个独特的“迭代预算”（Iteration Budget）机制。当工具调用的递归次数接近设定的上限（例如达到总预算的 80% 时），系统会在 `<tool_response>` 中强行注入“预算压力警告”。这会明确指示模型停止开启新的研究分支，尽快收敛逻辑并输出最终结果。

5. 递归循环 ：完成上述步骤后，Agent Loop 并不会结束

- 系统会将包含了工具调用结果的最新上下文再次发送给模型发起新一轮推理。
- 模型会读取工具的返回结果，评估任务进度：如果任务未完成，它会继续输出新的 `<tool_call>`；如果任务已完成，它会输出最终的自然语言总结。
- 这个“发送消息 -> 触发工具 -> 返回结果 -> 再次发送”的循环会一直同步递归执行，直到任务彻底完成或迭代预算耗尽为止。最终的完整执行轨迹和对话状态会被持久化保存到基于 SQLite 的 SessionDB 中。
  

## **1.2 记忆系统设计**


### 1.2.1 Hermes Agent的多层级记忆堆栈

1. **声明性/个人记忆（Declarative Memory）：** 使用本地的 `MEMORY.md`（环境事实）和 `USER.md`（用户偏好）。系统对这些文件施加了严格的长度限制（约 1300 Tokens 左右），并且要求 Agent 具备“自我修复”能力：主动清理过期内容、合并新知识，防止上下文无限膨胀。
2. **情景记忆（Episodic Memory）：** 基于 SQLite 数据库和 FTS5 全文搜索插件。它不依赖容易产生噪音的纯向量嵌入，而是将跨会话的历史记录通过关键字检索结合 LLM 语义总结后，再按需拉入当前上下文。
3. **程序化记忆（Procedural Memory / Skills）：** 基于 `agentskills.io` 开放标准的技能目录。当 Agent 成功完成复杂任务后，会自动反思并编写出一套包含步骤和排错指南的 `SKILL.md` 文件。系统采用“渐进式披露（Progressive Disclosure）”按需加载这些技能，节省 Token。
4. **关系型记忆（Relational Memory）：** 引入 Honcho 框架（作为 MemoryProvider 插件）进行“辩证式用户建模”。它不仅记录事实，还能通过 12 个身份层级追踪“用户与 Agent 关系的演变”，据此自动调整回复策略。

## 1.3 插件系统

Hermes Agent 的插件机制保证hermes的核心引擎保持精简，而复杂的第三方集成、记忆后端和自定义逻辑都通过插件来实现。

### 1.3.1 发现与加载&#x20;

Hermes 的系统会自动从以下三个来源发现并加载插件，无需开发者手动修改核心代码库：

+ **用户级目录**：`~/.hermes/plugins/`（适用于全局个人配置）。
+ **项目级目录**：`.hermes/plugins/`（适用于特定工作区或项目的专属插件）。
+ **Pip 包入口点 (Entry points)**：通过 Python 包管理器直接安装的第三方包。

### 1.3.2 分类

Hermes 将插件分为两大类，并对核心替换类插件实施了严格的管控：

+ **常规插件&#x20;**：用于为 Agent 提供基础扩展能力的轻量级模块。它们的作用是增强智能体与外部环境的交互手段或调整运行时的微小逻辑。可以通过上下文 API 自由注册工具、生命周期 Hooks 以及 CLI 命令。
+ **记忆提供商：** 一个抽象的集成接口，专门用于为 Hermes Agent 接入外部的第三方长期记忆后端，从而替代默认的本地 Markdown 记忆系统
  - 单选限制：为了防止工具 Schema 臃肿或后端写入冲突，系统规定同一时间只能激活一个记忆提供商。用户可以通过 `hermes plugins` 命令或修改 `config.yaml` 来切换激活的插件。
  - 通过并行的 `enrich_turn` 钩子提取记忆，然后使用 `<memory-context>` 标签对记忆进行净化和包裹，直接将其附加在当前这一轮的用户消息上，而不是系统提示词中
  - 在对话轮次完成后，使用守护线程（Daemon）触发 `on_turn_complete` 或 `on_memory_write` 进行后台异步数据同步（写入外部数据库），确保不阻塞 Agent 的主执行流。在上下文因触及长度上限而面临被压缩前，触发 `on_compress`，赋予记忆后端“抢救和提取关键见解”的最后机会，防止数据永久丢失
+ **上下文引擎：**&#x8D1F;责管理、优化和折叠大语言模型“上下文窗口”的核心处理引擎
  - 单选限制
  - Hermes 默认自带的上下文引擎是 `context_compressor.py`。当长跨度任务导致对话历史逼近模型 Token 阈值时，该引擎会介入，对对话历史中的“中间回合”进行有损的语义摘要压缩。它会剔除冗长的中间推理过程，只保留关键指令和工具调用状态，从而为 Agent 腾出宝贵的上下文空间以继续工作。
  - 如果开发者对默认的“有损压缩”算法不满意，可以通过开发新的 Context Engine 插件，将其替换为无损上下文管理或其他自定义的截断/摘要算法

### 1.3.3 核心赋能维度

一旦插件被加载，它可以从以下四个维度深度干预 Hermes 的运行：

+ **动态注入**工具&#x20;

插件可以通过实现 `get_tool_schemas()` 和 `handle_tool_call()` 接口，在 Agent 启动时将自己专属的工具动态注入到系统的全局 Prompt 中。当大模型决定调用这些工具时，请求会被路由回插件内部处理。

+ 深度介入**生命周期** Hook

插件系统暴露了极度丰富的 Hook，允许插件在对话的各个关键节点执行逻辑：

+ **核心执行前/后**：例如 `pre_llm_call` 和 `post_llm_call`，允许在发起 API 请求前后修改 Payload 或记录耗时。
+ **会话级 Hook**：如 `on_session_start` 和 `on_session_end`，用于会话的初始化和清理。
+ **记忆与压缩拦截**：&#x20;
  - `sync_turn`：在每轮对话完成后于后台守护线程执行（非阻塞），用于将对话同步到第三方数据库。
  - `on_pre_compress`：当上下文过长即将被截断压缩前触发，插件可借此拦截并提取重要见解进行持久化保存。
+ **无缝扩展命令行**

插件不仅仅影响后台逻辑，还能原生扩展 Hermes 的终端 UI：

+ 插件只需在自身目录下提供一个 `cli.py` 文件，并定义 `register_cli(subparser)` 函数，Hermes 在启动时就会自动发现并挂载这些命令。
+ 例如，Honcho 记忆插件注册了 13 个子命令。用户可以直接在终端输入 `hermes honcho status` 等专属命令。
+ 可见性隔离：只有当该插件被配置为“当前激活”状态时，它的专属命令才会出现在 `hermes --help` 的列表中，保持了 CLI 的纯净度。
+ 安全与交互式的**配置管理**

插件不需要开发者手动去环境变量里配置：

+ 插件可以通过定义 `get_config_schema()` 声明自己需要的配置字段。
+ 在安装或初始化时（如运行 `hermes memory setup`），系统会弹出一个向导，交互式地向用户索要这些字段。
+ 系统会自动将标记为 `secret: True` 的敏感信息（如 API Key）安全地写入宿主机的 `.env` 文件中，而将非敏感配置通过 `save_config()` 存入原生 JSON 配置中（如 `supermemory.json`）。

### 区分plugin、tool和skill

* Tool = 具体可执行动作
* Plugin = 给 Hermes 增加/修改动作与流程的扩展层
* Skill = 告诉模型如何组合这些动作去完成任务的任务方法层


## **1.4 Hook 生命周期**


Hermes 的 Agent Loop 暴露了丰富的生命周期 Hook（位于 `gateway/hooks.py` 等文件中），允许插件在关键节点介入并执行严格管控的线程逻辑。 针对最核心的记忆提供商（MemoryProvider），其 Hook 生命周期和线程契约有着明确的规范：

+ initializ&#x65;**：** 在 Agent 启动时在主线程（串行）调用，无时间限制，用于建立连接和准备状态。
+ enrich_turn **：** 在每次 LLM API 调用前于 **ThreadPool（并行）** 中执行，有严格的 **5秒超时**限制。它负责将净化的记忆区块（Memory Context）注入给用户消息，且不污染全局 System Prompt。
+ on_memory_write&on_turn complete **：** 在对话轮次完成后于 **Daemon 守护线程** 中触发（Fire-and-forget，不阻塞主流程），用于向后端同步会话和写入长期记忆。
+ on_compress **：** 在上下文即将被压缩截断前触发，运行在**非 Daemon 线程**（会阻塞压缩，最大 120 秒），确保 Agent 有最后的机会将重要见解（Insights）保存到后端，防止数据永久丢失。
+ shutdown **：** 在进程退出前在**主线程**触发（15 秒超时限制），确保所有挂起的记忆写入操作被安全刷盘。
